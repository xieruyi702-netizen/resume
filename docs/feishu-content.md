# 语音匹配服务与美食汇——简历项目详细描述

本文档按简历条目顺序展开，每条含背景与问题、技术方案、高频追问与标准回答。数字口径：组件级压测与端到端 JMeter 分开叙述，面试主动分清。

## 一、超级匹配延迟弹窗

### 背景与问题

付费玩法：用户购卡后延迟推送高质量候选，希望"点过去对方确为我预留"。热门候选稀缺、被并发流程争抢；延迟期间锁可能过期；要防同一用户被反复弹窗。

### 技术方案

- 延迟队列闭环：Redis ZSet（score = 触发时刻），入队顺带清理过期脏任务；Lua 原子批量弹出（ZRANGEBYSCORE + 按 member ZREM，防多实例重复消费与同分误删）；任务入独立线程池并发推荐。线程池参数：核心 20 / 最大 400 / 队列 100 / keepAlive 300s / CallerRunsPolicy——队列刻意小，溢出由调度线程自执行形成背压（任务仍在 ZSet 不丢）；调度器独立（poolSize=5），优雅关闭等 120s。
- 提前锁定付费候选：存在性预检（被锁直接跳过省一次计算）+ 双向预订锁（SET NX EX 原子加锁）+ 延迟期 TTL 续期（防预订比锁先过期）+ 结束 Lua 校验归属释放；锁冲突自动换候选，另有实验开关控制"预订失败是否放行"（严格/宽松预订权衡）。
- 跨服务频控：发送/曝光双 Redis key 由 reco 写、link 管线前置读，主叫拦截 + 防重复弹窗。
- 动态参数：批量大小、消费开关、阈值经 Apollo 下发——积压调大批量、下游过载关开关止血（任务持久在 ZSet 不丢）。

### 高频追问与标准回答

问：锁过期任务没跑完怎么办？
答：锁是体验互斥不是资金正确性；正确性由频控去重与支付幂等兜底，双写也会被拦。

问：为什么队列只有 100？
答：溢出 CallerRuns 天然背压——拒绝即让生产速率慢下来，且任务有 ZSet 底不丢。三层（ZSet/队列/CallerRuns）语义各管一层。

## 二、免费男性延迟匹配 UCB 工程化

### 背景与问题

免费用户即时推送接通率低，延迟过短质量差、过长易流失；且不同付费等级耐心不同。建模为 7 臂老虎机（延迟 20~50s），按付费等级 HIGH/MID/LOW 分段独立学习。公式与 reward 算法定义，后端负责工程化。

### 技术方案

- 选臂：UCB1（均值 + α·sqrt(ln N / count)），冷启动 count<3 优先试满——防 count=0 除零与无均值死锁；统计按付费分段 + modelVersion 分桶存独立 Redis Hash，支持版本双跑灰度与重置回滚。
- reward：ln(成交卡片总价+1)，组合卡型（10+11 打包 15 币）硬编码真实价，ln 压缩重尾防大额用户绑架均值；未购买 total=0 天然得 0 分。
- 结算：支付/挂断回调异步触发，Lua 单次往返完成查 pending → 累加臂统计 → 清 pending——防回调与过期清理并发双结算；pending TTL + 定时批量清理双层保障，统计窗口无脏数据。
- 兜底：资格/配置/Redis 读/写 pending 四类失败一律降级固定延迟，按原因分别打点——策略可实验，稳定性无条件。

### 高频追问与标准回答

问：为什么 UCB 不是 ε-greedy？
答：ε-greedy 均匀随机探索，明显差的臂也反复试；UCB 加分项让探索偏向试得少的臂，收敛更快。Thompson 要维护 Beta 分布实现重，UCB 只需计数 + 均值。

问：统计丢失了怎么办？
答：modelVersion 重置 = 全臂重新冷启动，21 次匹配重新学出；UCB 对统计清零自愈能力强。

问：支付慢于归因窗口怎么办？
答：归因看 pending 记录不看支付时间——10s 臂促成的匹配，用户 20s 后付款照样记 10s 臂；支付时间只区分快速成交/常规成交。硬边界是 pending 的 1 小时 TTL，超时放弃归因——归因窗口宁可短不可错。

## 三、可视化平台 Kafka 消费与查询优化

### 背景与问题

推荐全链路 debug 消息（单条上千行候选明细）落 MySQL 供回放；旧消费逐行 INSERT + 同步 Hive 转发，两头 IO 串行拖住消费线程，高峰 lag 持续上涨；部分失败静默丢数；查询轮询占满 HTTP 线程。

### 技术方案

同 poll 批内合并后 500 条/块批量 INSERT；Hive 回写迁出消费线程（异步批量 + 重试）；子批失败整批不 ack、DuplicateKey 幂等成功；止血改 pause/resume 消费容器（offset 不动）避免静默丢数；列表 N+1 改批量 IN；simulate 去掉服务端长轮询改立即返回 + 事件触发。

### 标准回答

问：异步回写崩溃丢数据怎么办？
答：Hive 明细是离线分析旁路非资产数据，重试覆盖抖动、极端丢失从 MySQL 事实源离线补偿——主链路 at-least-once、旁路尽力而为，是刻意的成本分层。

问：pause/resume 代价？
答：维护期 lag 上涨是预期现象且会消化——止血手段本身不能成为新故障源。

## 四、实验策略 Agent

### 背景与问题

策略评估纯人工半天起步。两层建设：跑批平台解决执行慢；Spring AI 取数 Agent 解决"写 SQL"本身。

### 技术方案

- 平台：多线程跑批 + 异步飞书（端到端约 −89%）；cron 存 MySQL，ThreadPoolTaskScheduler + CronTrigger 动态注册/重载，改周期不重启生效。
- 知识层职责分离：业务表摘要向量化按需检索（约 200 份文档，Spring AI EmbeddingModel 对接内部向量服务 + VectorStore 精确检索）；指标口径与规范作常驻提示词防口径漂移（全局标准不能依赖某次检索命中）。
- 生成链路：自然语言需求 → 检索 top-k → 组装上下文 → 生成 SQL → 直查 Hive EXPLAIN + 试跑。

### 质量评估与标准回答

评测集：真实历史取数需求 + 业务方核实结果判卷（跳过 gold SQL 标注）。准确率约 90%、越界拒答约 95%——错误四类归因：检索漏（改 summary 归零）/知识过时（挂变更流程）/模型推理错（规则压缩 + 验证兜底，占两成，是 90% 天花板原因）/需求超覆盖（正确拒绝并收集）。标准回答（为什么不用向量数据库）：200 条向量精确检索零点几毫秒，ANN 是百万级方案——选型跟规模走。

## 五、个人项目：美食汇｜高并发美食优惠券 + 食谱 RAG Agent

### 项目定位

高并发读写与检索增强问答放在同一业务壳里练完整闭环：Java 侧券详情读（多级缓存）、秒杀写（限流 + Lua + 订单闭环）、支付后 Kafka 异步加积分；Python 侧 HowToCook 菜谱（约 369 道 Markdown）切片建库、双路召回、LangGraph ReAct Agent、分层记忆与 OOD 拒答。

### 读链路与秒杀防护

布隆本地快照拦非法 id → L1 Caffeine → L2 Redis 从库轮询（失败回主）→ MySQL 互斥重建 + 空值缓存 + TTL 抖动防雪崩；更新走先更 DB → 删 L2 → pub/sub 踢各实例 L1。限流令牌桶/漏桶可切换（令牌桶偏突发、漏桶更平滑，同参压测验证实现），热路径 Redis Lua 一次完成库存判定/一人一单/扣减。

### 订单闭环

抢券同事务落待支付订单，返回即可支付；状态机含用户取消；支付幂等（CAS 防双扣）；ZSet 延迟取消 + CAS/Lua 回补；支付成功 Kafka 异步加积分（points_status 兼投递标记，消费幂等/死信）；用户余额 Cache Aside + 锁内扣充；雪花订单号时钟回拨拒发号。

### 食谱 Agentic RAG

HowToCook 切片建库；关键词 BM25 + 向量双路召回 RRF 融合；LangChain/LangGraph ReAct Agent（生成 DeepSeek V4 Flash）；记忆按用户隔离——短期 Redis（TTL + 条数淘汰），长期 Chroma 向量召回 + 每用户上限淘汰，上下文按预算比例组装（长期忌口优先）；库外菜与非美食问题 OOD 拒答；证据不足才 web_search 且本地优先。

### 指标与评测

JMeter 64 线程真实漏斗约 3.1k req/s、P99 112ms（Err 0%，余额对账 OK）；Agent Hit@1≈0.90 / Hit@5≈0.96 / MRR≈0.91，Judge（GLM-5.3-Flash 跨源，生成 DeepSeek V4 Flash）抽样均分≈0.82，拒答≈0.90；评测集 100 题（库内 70 + 库外菜 15 + 非食谱 15，带参考答案）。

### 高频追问与标准回答

问：组件级高 QPS 和 JMeter 3.1k 矛盾吗？
答：前者是进程内 L1 命中的物理上限；后者含 Nginx、双实例、限流、同步建单、支付事务全链路——主动分两套口径。

问：记忆会串用户/无限涨吗？
答：不会。Redis key 与 Chroma query 都带 user_id 隔离；短期 LTRIM + TTL，长期每用户上限删最旧；不可用时进程内兜底评测仍可跑。

问：评测集为什么混库外菜和非食谱？
答：闭集 RAG 必须会拒答，否则线上乱编比答错更危险。

问：Judge 会偏袒生成模型吗？
答：刻意跨源（生成 DeepSeek、Judge GLM），固定温度与提示词只对照参考答案打分；简历写抽样均分不夸成满分。

### 已知边界（主动承认）

Redis 未做持久化重建（重启需重建库存/去重集合）；限流为实例内存态；OOD 拒答依赖菜名重合等启发式，近义库外菜仍可能偶发误召回，靠评测与门控持续收紧。
