## 五、个人项目：美食汇｜高并发美食优惠券 + 食谱 RAG Agent

### 5.0 项目定位与背景

个人项目，把「高并发读/写」和「检索增强问答」放在同一业务壳子里练完整闭环：

- **业务壳**：美食优惠券秒杀 + 食谱问答助手（品牌名美食汇）。
- **Java 侧**：Spring Boot 3 + MyBatis；Redis 一主两从；Kafka；MySQL；Docker Compose 编排（Nginx 轮询 + app1/app2 双实例 + 中间件）。完整链路——券详情读（多级缓存）、秒杀写（限流 + Lua + 同步待支付订单）、支付/取消（状态机 + ZSet）与支付后 Kafka 加积分。
- **Python 侧**：基于 HowToCook 开源菜谱 Markdown（约 369 道）切片建库；关键词 BM25 + 本地 BGE 向量双路召回；**LangChain / LangGraph ReAct Agent**；生成模型 **DeepSeek V4 Flash**，评测 Judge **GLM-5.3-Flash**（跨源）；分层记忆 + OOD 拒答；评测集 100 题。

设计原则：每个关键决策尽量有「压测数字」或「对账/评测结果」可复现；组件级 QPS 与端到端 JMeter 数字分口径，面试主动说清。

### 5.1 券详情读链路（多级缓存）——对应简历第 1 条

#### 背景与问题

秒杀场景读远多于写，券详情是典型热点：若直打 MySQL，连接与磁盘会先于库存逻辑被打满。目标是把合法热 key 的读拦在近端，同时挡住非法 id 扫库（穿透）、热点重建打爆（击穿）、大量 key 同时过期（雪崩）。

#### 技术方案

链路顺序：**布隆本地快照**（非法 id 直接拒，零网络）→ **L1 Caffeine**（进程内，短 TTL，热 key 微秒命中）→ **L2 Redis 从库**（跨实例共享；轮询读，失败回退主库）→ **MySQL**（互斥锁重建 + 空值缓存防击穿；TTL 随机抖动防雪崩）。

多级缓存的**作用**一句话：L1 吃住最热流量、护住本机延迟；L2 做实例间共享与读扩容；DB 只做兜底真相源。更新：先更 DB → 删 L2 → pub/sub 广播踢各实例 L1；pub/sub 至多一次，丢消息退化为短 TTL 自然过期。

#### 分层贡献（组件级，2026-09-06）

8 线程 × 5s，进程内直调；约 10% 非法 id。口径与 JMeter 全链路不可比。

| 层级 | 路径 | QPS | P50 | P99 |
|---|---|---:|---:|---:|
| 1) 仅 MySQL | 直连 DB | **2.1 万** | 347µs | 888µs |
| 2) MySQL + Redis | 跳过 L1，热数据打 L2 | **2.8 万** | 271µs | 1.4ms |
| 3) MySQL + Redis + 进程内 L1 | 全链路热 L1 | **145 万** | ~0µs | 4µs |

结论：L2 相对直连有增益但仍受网络 RTT 约束；**数量级提升来自 L1**。复现：`--bench=cache --threads=8 --duration=5`。

#### 高频追问

**问：为什么要三级，两级不够吗？**  
答：布隆挡的是「根本不存在的 id」，和「存在但冷」不是一类问题；L1 解决跨进程重复打 Redis；L2 解决多实例共享。少一层就会在非法扫库或热 key 网络往返上露出短板。

**问：本地布隆和 Redis 布隆怎么选？**  
答：读路径要零 RTT，所以启动/周期从 Redis Bitmap 拉快照到本地 BitSet；写仍走主库 pipeline。一致性靠短窗口可接受的误判与重建。

**问：缓存更新用删缓存还是改缓存？**  
答：删缓存（Cache Aside）：更新路径简单，避免并发写脏；短暂穿透由互斥锁与空值缓存兜住。

**问：L1 命中百万级 QPS 怎么解释？**  
答：那是**组件级、本地内存命中**的物理量级（复测约 145 万 QPS），证明热 key 不走网络；不是「系统能扛百万并发」。端到端以 JMeter 全链路口径为准（约 3.9k req/s）。

### 5.2 秒杀入口防护——对应简历第 2 条

#### 背景与问题

开闸瞬间写流量尖峰：没有入口限流，Lua/Redis/下游会被无效请求淹没；没有原子扣减，并发下会超卖。多实例还要保证负载均衡与一人一单。

#### 技术方案

- **接入**：Nginx 轮询 app1/app2（失败摘除 + next_upstream）。
- **限流**：令牌桶 / 漏桶双算法可切换，惰性补充、无后台线程；均 **fail-fast**（拿不到立即拒绝，不排队拖垮线程）。令牌桶偏容量内突发，漏桶偏平滑出水。切换：`POST /admin/rate?mode=token|leaky`。
- **对比压测数据**（同参：容量 200 / 速率 2000/s，64 线程灌 50 万请求，组件级 `tryAcquire`，不经 HTTP）：

| 算法 | 通过 | 拒绝 | 说明 |
|---|---:|---:|---|
| **令牌桶** | **≈361** | ≈499,639 | ≈ 容量 200 + 灌注窗口内补充量，与公式吻合 |
| **漏桶** | **同量级（≈280–360）** | 其余拒绝 | 空桶起灌，突发被水位顶住，出水更平滑 |

  二者均 fail-fast、无阻塞排队。切算法主要改变写入口突发放行形态；全链路混合吞吐仍由读缓存与异步写主导（限流未成瓶颈时 `rejected≈0`，整体 QPS 差异更多来自噪声）。
- **热路径**：Redis **Lua** 一次往返完成库存判断、一人一单、扣减——并发下不可能超卖。

#### 高频追问

**问：令牌桶和漏桶怎么选？**  
答：要允许开闸尖峰用令牌桶；要保护下游被打成尖刺用漏桶。本项目做成可切换，用同参压测证明实现正确，而不是教条二选一。

**问：限流为什么不做到 Redis 集群全局？**  
答：当前是实例内存态，集群总限流 ≈ 单实例 × 实例数，这是已知边界。全局限流要另做 Redis/网关令牌，复杂度和运维成本更高；面试主动承认边界。

**问：为什么扣减用 Lua 不用 DB 乐观锁？**  
答：热路径要极短 RTT；Lua 把「判库存 + 一人一单 + 扣减」原子化。落库走异步，用 Outbox/幂等保证最终一致，而不是在同步路径上打 DB。

### 5.3 异步落库与订单闭环——对应简历第 3 条

#### 背景与问题

Redis 扣减成功后如果进程崩溃、消息没发出，会出现「库存没了但没有订单」。支付与超时取消要状态机清晰，取消后库存能安全回补且不超补。

#### 技术方案

- **订单与积分**：抢券热路径同事务落待支付订单 + lockStock，返回即可支付（无独立消息表）。状态：0 待支付 / 1 已支付 / 2 超时取消 / 3 用户取消。支付成功后投 Kafka 加积分；订单 `points_status` 标记待入账/已入账，中继扫未入账已支付单重投；消费端事务内 CAS+加分，失败进死信。
- **余额支付**：用户余额读走 **Redis（Redisson RAtomicLong）** Cache Aside；扣款/充值用 **Redisson 分布式锁**，锁内 MySQL CAS，成功后**删缓存不回写**；商铺余额仍只在 MySQL。
- **单号**：雪花算法（workerId 注入）；**时钟回拨拒发号**，避免双实例撞号/回拨乱序。

#### 高频追问

**问：为什么不直接发 Kafka，还要本地消息表？**  
答：先落库再发，崩溃可中继重投；Kafka 发送失败不丢「意图」。消费侧幂等吸收重复。

**问：at-least-once 会不会重复下单？**  
答：会重复投递，靠订单唯一索引 / INSERT IGNORE 幂等；对账用「redis 余量 + 生效订单 = 初始库存」验收。

**问：延迟取消多实例会不会重复取消？**  
答：扫描侧分布式锁互斥；取消与回补 Lua/CAS 幂等，重复执行不多扣、不多补。

**问：支付怎么保证余额扣对、商铺入账不漏？**  
答：同一事务：先查待支付订单与券的 `price/shop_id` → 用户 `UPDATE ... WHERE balance>=price`（0 行即余额不足）→ 商铺 `balance+=price` → 订单 CAS 落 `amount/shop_id` → 库存转换；任一步失败整单回滚。Redis 延迟队列在 **afterCommit** 再删，避免库回滚后队列已清。

**问：Lua 里扣减库存和一人一单是一步吗？后一步失败怎么办？**  
答：对客户端是一次原子脚本（中间无别的命令插入）。但 Redis **不会**在脚本中途报错时自动回滚已执行写。本项目顺序是先 `SADD` 再 `DECR`：若 `DECR` 因 WRONGTYPE 等失败，可能出现「集合有人、库存未扣」。正常路径两命令几乎都会成功；脚本内用 `redis.pcall` 捕获后 `SREM` 撤回占坑，再加定时对账兜底。

**问：回补 Redis 库存、去掉去重标记要加锁吗？**  
答：一般不需要应用锁。回补 Lua：`SREM` 成功才 `INCR`，对外原子且对重复调用幂等。同样不提供中途报错自动回滚；键类型破坏时需对账修复。

**问：Lua 没有回滚，项目怎么补？**  
答：两层——① 脚本内 `redis.pcall`：先 `SADD` 再 `DECR`，`DECR` 失败则 `SREM` 撤回占坑；回补 `SREM` 后若 `INCR` 失败则 `SADD` 加回。② 定时 `InventoryReconciler`：不变量 `stock+SCARD(users)==初始库存`；和偏大则移出无订单/无消息的幽灵用户（比「匿名少货」更好对账）。手动：`POST /admin/reconcile`。

### 5.4 食谱问答 Agent（分层记忆）——对应简历第 4 条

#### 背景与问题

只做「检索 + 拼接生成」时，模型不会主动换策略（换检索路、精读全文、读记忆），也难处理「这道菜步骤呢」指代和忌口偏好。要用工具化 Agent，但要轻量、可讲清，避免框架黑盒。

#### 技术方案

- **知识库**：[HowToCook](https://github.com/Anduin2017/HowToCook) Markdown → 菜谱/切片 JSONL；约 369 道菜。
- **检索**：jieba+BM25 关键词路 + 本地 `bge-small-zh-v1.5` 向量路，RRF 融合；Agent 也可单路调用。
- **Agentic**：**LangChain StructuredTool + LangGraph `create_react_agent`**；工具含检索 / `get_recipe` / `get_section` / `recall_memory` / 可选 `web_search`。
- **分层记忆（按用户隔离）**：
  - **回合内**：LangGraph messages 承载本轮工具观察；
  - **会话短期**：独立 Redis（`redis-memory:6382`，与秒杀主从隔离）；Key `mem:u:{user}:s:{session}:turns/work`；焦点菜指代；
  - **用户长期**：专用 Chroma 向量库（`chroma_ltm`），metadata 带 `user_id` 过滤；忌口/偏好/拒答教训语义召回。
- **上下文组装**：`ContextAssembler` 按预算拼注入块——**长期约束优先 → 近轮会话**，总字符封顶（默认 2000），避免挤占检索证据位；Agent 系统提示先吃记忆块，检索结果走 tool 观察。
- **拒答**：库外菜、非食谱问题门控拒答，避免编造步骤/用量。

#### 高频追问

**问：为什么用 LangChain？**  
答：用 LangGraph ReAct / tool-calling 托管多步工具循环与消息态，检索与读菜谱仍是自研 `RecipeTools`（BM25+向量+RRF），框架管编排、业务工具可单测。实习侧 Agent 是 **Spring AI**，与项目二栈分开讲。

**问：短期记忆怎么淘汰？**  
答：两层——① 条数：`LTRIM` 只保留最近 N 轮（默认 12）；② 时间：每次写入刷新 Key TTL（默认 24h），过期整会话清空。Redis 侧还可配 `maxmemory-policy allkeys-lru` 兜底。

**问：长期记忆怎么淘汰？写向量库会不会无限涨？**  
答：每用户硬上限（默认 200 条）；写入后按 `ts` 删最旧。检索 `where={user_id}`，与别的用户物理隔离在同一 collection 的 metadata 过滤上。

**问：上下文一般怎么组装？**  
答：工业常见顺序是：系统策略 → 长期硬约束（忌口）→ 会话近轮/焦点 → 当前问题；证据（检索 chunk / 全文）不塞进记忆预算，由工具观察带回。超预算时**先保长期、截短期**，因为忌口比闲聊更不能丢。

**问：长期记忆会不会污染别的用户？**  
答：不会。Chroma query 带 `user_id` filter；Redis Key 也带 `user_id`。评测 `persist_session=False` 且每题独立 user/session，避免串题。Redis/Chroma 不可用时进程内兜底，评测仍可跑。

**问：网页搜索会不会覆盖本地菜谱？**  
答：策略是本地优先，证据不足才 web_search，并要求注明网络来源；主答案仍以知识库为准。

### 5.5 指标与评测——对应简历第 5 条

#### 口径

- **Java 全链路**：JMeter 64 线程 / 30s / 真实漏斗（浏览 + 抢券同步建单 + 延迟支付），约 **3.9k req/s**、P99 **62ms**、Err 0%；已支付笔数与 pay 一致，余额对账 OK。
- **组件级缓存分层**：仅 MySQL ≈2.1 万 / 仅 L2 ≈2.8 万 / 热 L1 ≈145 万 QPS（见 5.1）。
- **Agent**：测试集 100（库内 70 + 库外菜 15 + 非食谱 15），题面带标准参考答案；检索 Hit@1≈0.90 / Hit@5≈0.96 / MRR≈0.91；生成 **DeepSeek V4 Flash**，Judge **GLM-5.3-Flash** 抽样均分≈0.82；库外/OOD 拒答≈0.90。

#### 高频追问

**问：组件百万级 QPS 和 JMeter 3.9k 矛盾吗？**  
答：不矛盾。前者是进程内 L1 命中的物理上限；后者含 Nginx、双实例、限流、同步建单、支付事务等全链路。面试要主动拆开两套口径。

**问：评测集为什么混库外菜和非食谱？**  
答：闭集 RAG 不仅要答对库内题，还要会拒答；否则线上乱编比答错更危险。

**问：Judge 会不会偏袒自己的生成模型？**  
答：刻意跨源——生成用 DeepSeek V4 Flash、Judge 用 GLM-5.3-Flash，并固定温度/提示词只对照参考答案打分；简历写抽样均分，不夸成满分。

### 5.6 已知边界（面试主动承认）

- Redis 未做持久化重建时，重启后库存/去重集合需运维恢复或重建逻辑（当前教学项目可说明边界）。
- 限流为实例内存态。
- Agent 拒答依赖菜名重合等启发式，近义库外菜仍可能偶发误召回，靠评测与门控持续收紧。
